# Gotchas

- **Не все vanilla-билды покрыты определениями DBC.** `wowdev/WoWDBDefs` покрывает релизные 1.x (`Talent.dbd`: `1.0.0.3980–1.12.3.6141`) и часть альфы (вплоть до `0.7.0.3694`), но не гарантированно всё. `suprsokr/VanillaDBDefs` — специализированный репозиторий, но **только для релизных 1.0–1.12.3, альфа/бета там нет вообще**. Для непокрытых альфа-билдов нужен собственный минимальный WDBC-ридер, структуру которого выводить вручную по сырому `.dbc` файлу конкретного клиента — закладывать на это время отдельно, не как быстрый fallback.
- **Иконки нельзя просто перезаписывать по имени.** Одна и та же иконка (`SpellIcon.dbc` name → `Interface\Icons\*.blp`) используется многими талантами и повторяется почти без изменений во всех билдах. Наивная экстракция будет декодировать и писать один и тот же арт заново на каждый билд. Решение — таблица `icon_sources(mpq_path, source_hash, icon_path)`: если sha256 сырых байт `.blp` не изменился с прошлого прогона — не декодировать BLP и не писать файл, просто переиспользовать существующий `icon_path`. PNG именуются по sha256 своего содержимого (естественная дедупликация) и никогда не удаляются.
- **Claude Code в этой сессии не может выполнять Windows-бинарники (`dotnet.exe` и т.п.).** Диски `/mnt/c`, `/mnt/e` примонтированы через 9p/drvfs (чтение/запись файлов работает нормально), но WSL-интероп для запуска `.exe` не подключён (`cat /proc/sys/fs/binfmt_misc/WSLInterop` — пусто). Значит: код в `extractor/` пишется агентом как обычно, но `dotnet build`/`dotnet run`/любые прогоны на реальных клиентах пользователь должен выполнять сам в своём реальном WSL/PowerShell-терминале, не через агента. `dotnet.exe` там лежит по путям `/mnt/c/Program Files/dotnet/dotnet.exe` и `/mnt/c/Program Files (x86)/dotnet/dotnet.exe` (видны из этой сессии только как файлы, не как исполняемые).
- **КРИТИЧНО: `row.ID`/ключ словаря в `DBCD` для vanilla WDBC-таблиц НЕ равен реальному значению поля ID.** Баг в самой `DBCD.IO` (`WDBCReader.cs`/`FieldCache.cs`): `WDBCRow.Id` инициализируется как `recordIndex + 1` (порядковый номер записи в файле), и переопределяется реальным значением из данных **только** если поле помечено `$noninline,id$` в `.dbd`. У всех vanilla-таблиц (`Talent`, `TalentTab`, `Spell`, ...) в `.dbd` стоит просто `$id$` (без `noninline`) — то есть для WDBC-формата это ВСЕГДА "инлайновый" ID, но баг(?)/особенность `DBCD.IO` не считает это основанием обновить ключ. Итог: `storage.TryGetValue(id, ...)`, `storage[id]` и `row.ID` **все врут** для vanilla-таблиц — отдают не ту запись/не то число.
  Подтверждено на `1.12.1.5875`: физически первая запись `Talent.dbc` имеет реальный `ID=26` (сверено побайтово), но DBCD выдавал для неё `row.ID=1`. Из-за этого `Spell.dbc`-лукап по ID (`storage[11069]`) возвращал случайную запись на позиции 11069, а не спелл с реальным ID=11069 — так появилось имя `"Increased Nature Resist 31"` вместо настоящего `"Improved Fireball"`. **Более серьёзно**: `PrereqTalent`-ссылки в `Talent.dbc` указывают на реальные ID других талантов — если сверять их с `row.ID` (сломанным), граф пререквизитов дерева был бы полностью неверным.
  **Фикс** (`Extractor.Dbc.DbcClient`): само значение поля ID читается ПРАВИЛЬНО как обычное поле через `row.Field<int>("ID")` (это не пострадало — баг только в том, что оно не используется как ключ словаря/`row.ID`). Строим свой индекс `Dictionary<int, DBCDRow>` вручную по `row.Field<int>("ID")` при каждой загрузке таблицы (`LoadIndexedById`), не полагаемся на `storage[id]`/`row.ID` нигде.
  **Ранее записанная "проверка" (spell 11069 = Improved Fireball, сверено с wowhead) была методологически шаткой дважды**: (1) сверялась с wowhead.com/classic — это база официального переиздания 2019 года (билды 1.13.x+), а не оригинальной vanilla 2006 (это разные ID-пространства, `WoWDBDefs` явно их разделяет отдельными LAYOUT-блоками); (2) на момент той проверки баг с ID выше ещё не был найден. Факт оказался верным СЛУЧАЙНО. После фикса пересверено напрямую на данных **этого же клиента** — сходится: talent ID=26 → tab ID=41 ("Fire", Mage) → spell 11069 = "Improved Fireball" Rank 1, с корректной прогрессией по рангам 1-5.
- **`ChrClasses.PlayerClass` — не "номер класса для classMask", вопреки названию.** Ожидаемо было, что `classMask = 1 << (PlayerClass - 1)` — но на реальных данных `PlayerClass=1` у ВСЕХ 9 классов на `1.12.1.5875`. Это, судя по всему, булевый флаг "является ли играбельным классом", а не число для сдвига. Правильная формула (проверена — совпадает 1:1 с `classMask` из `TalentTab.dbc`): **`classMask = 1 << (ChrClasses.ID - 1)`**, используя сам `ID` строки, не `PlayerClass`. Не путать имя поля с его реальной семантикой — проверять на данных, не полагаться на название.
- **DBCD: locstring-поля (`Name_lang`, `Description_lang` и т.п.) без явного `Locale` возвращаются как `string[]`, не `string`.** `dbcd.Load(table, build)` по умолчанию `Locale.None` — тогда `row.Field<string>("Name_lang")` падает с `RuntimeBinderException: Cannot convert type 'string[]' to 'string'`. Нужно всегда передавать локаль явно: `dbcd.Load(table, build, Locale.EnUS)`.
- **`TalentTab.dbc` имеет СВОИ три vanilla-layout'а, границы не совпадают с границами `Talent.dbc`** (у Talent слом один — между `0.9.1.3810`/`0.10.0.3892`; у TalentTab их два, в других местах): `0.7.0.3694–0.7.6.3712` — без `BackgroundFile` и `OrderIndex`; `0.8.0.3734` (только этот один билд) — есть `BackgroundFile`, `OrderIndex` ещё нет; `0.9.0.3807` и далее — есть оба. Обрабатывается так же, как `RequiredSpellID` у Talent — через `storage.AvailableColumns.Contains(...)` перед чтением, никогда не через собственную build-range логику (DBCD сам разбирается по `.dbd`).
- **Talent-UI разделили на отдельный LoadOnDemand-аддон между `1.7.1.4695` и `1.8.0.4735`** — не связано с изменением структуры `Talent.dbc` (это отдельная ось, см. ниже). До `1.8.0.4735` весь код жил в `Interface\FrameXML\TalentFrame.lua` (567 строк, часть базового интерфейса). C `1.8.0.4735` логика переехала в `Interface\AddOns\Blizzard_TalentUI\` (`## LoadOnDemand: 1`), а старый файл в `FrameXML` патч **физически обнулил** (проверено: пустой файл вместо 567 строк) — часть общего для той эпохи паттерна выноса тяжёлых панелей в ленивые аддоны. Для нашего экстрактора не критично (мы не парсим Lua/XML), но полезно для фронтенда: в `Blizzard_TalentUI.lua` зашиты константы грида — `NUM_TALENT_COLUMNS=4`, `MAX_NUM_TALENT_TIERS=8`, `TALENT_BUTTON_SIZE=32px` (см. architecture.md).
- **На `0.7.0.3694` бо́льшая часть талантов — не финальный контент, а плейсхолдеры Blizzard.** Проверено на реальных данных после `extract-build`: 137 из 145 извлечённых рангов (94%) имеют имя вида `"PH Arcane Concentration"` (PH = PlaceHolder) и описание, начинающееся с `"Test:"`. Это не мусор и не баг экстрактора — буквально то, что лежит в клиенте: дерево уже имеет структуру (тиры/колонки/пререквизиты), но большинство абилок ещё не реализованы, только описаны текстом-заглушкой. Настоящий финальный контент на этом билде — единицы (`Critical Mass`, `Pyroblast`, `Blast Wave`, `Ice Barrier` у Mage). Заодно подтверждает раньше найденный факт: у Talent #31 ранги 4-5 ссылаются на несуществующие в `Spell.dbc` ID (11111/11112) — соответствующая способность на этом этапе разработки ещё физически не закодирована, и наше правило "пропускать с логом, не выдумывать" сработало ровно для этого случая.
- **До `0.7.0.3694` "таланты" — не грид, а тренер, извлекать нечего.** Патчноуты упоминают таланты уже в 0.5.4, но в клиентах `0.5.3.3368` (Friends & Family Alpha, конец 2003 — уже есть ранние UI-хуки вроде микрокнопки талантов, но полноценного дерева ещё нет) и `0.5.5.3494` нет `Talent.dbc` вообще — вместо этого есть `Interface\FrameXML\TalentTrainerFrame.lua/.xml`. Подтверждено чтением самого lua: это классический механизм NPC-тренера (`IsTalentTrainer()`, `GetTrainerServiceInfo()`, `UnitCharacterPoints("player")`) — точно как обычный тренер способностей, никакого клиентского DBC с деревом/пререквизитами/tier-структурой не существует, данные приходили с сервера в рантайме. Для нашего проекта (грид-дерево с прокликиванием) в этих билдах извлекать физически нечего — это не пробел в экстракторе, а честная граница источника. DBC-driven дерево талантов (`Talent.dbc`, tier/column/prereq) стартует ровно с `0.7.0.3694`.
- **Патчей может быть N штук, не 2, и имя файла регистро-зависимо на Linux.** Изначально код был захардкожен на `["patch.MPQ", "patch-2.MPQ"]`. Оказалось: (1) у части ранних альфа-клиентов файл называется `patch.mpq` (нижний регистр) — на регистро-чувствительной ФС (`ext4`/`9p`, в отличие от Windows) `File.Exists("patch.MPQ")` для них тихо возвращал false, патч просто не применялся, без единой ошибки; (2) в принципе патчей может быть больше двух (privatny-сервера/поздние клиенты — `patch-3.MPQ` и далее). Исправлено в `Extractor.Mpq.PatchChain.ApplyAll(archive, dataDir)` — сканирует директорию регэкспом `^patch(-(\d+))?\.mpq$` с `RegexOptions.IgnoreCase`, применяет в порядке `patch → patch-2 → patch-3 → ...`, сколько бы их ни было. **Все места, открывающие DBC-архив, должны использовать `PatchChain.ApplyAll`, а не свой список имён.** На проверенном наборе клиентов данные для Talent/TalentTab не изменились после фикса (эти конкретные `patch.mpq` их не трогали) — но баг был реальным и мог тихо испортить другие таблицы.
- **Таланты появлялись у классов не одновременно — датировано по `TalentTab.dbc` (`classMask`):**
  - `0.7.0.3694–0.7.6.3712` — только Mage
  - `0.8.0.3734` — + Warrior
  - `0.9.0.3807–0.9.1.3810` — + Rogue, Priest
  - `0.10.0.3892` — + Shaman, Druid
  - `0.11.0.3925–1.0.1.3989` — + Warlock (7 из 9 классов; ещё нет Paladin/Hunter)
  - `1.1.0.4044` — + Paladin, Hunter → все 9 классов, дальше без изменений до `1.12.2.6005` (**уточнено**: изначально было записано "1.1.1.4062" — это было верно только для набора клиентов, доступного на тот момент; после получения `1.1.0.4044` выяснилось, что граница на билд раньше. Проверять эмпирически, не доверять прошлой записи без переклиента, если появляется билд между уже проверенными)

  **Важный нюанс**: "данные существуют в клиенте" ≠ "фича была реально доступна игрокам". По патчноутам 0.8.0: _"Talents are now available for the Warrior and Mage classes! ... Talents will eventually be available for all classes."_ — то есть кнопка/хоткей ("N") для открытия окна талантов появились только в 0.8.0, хотя маговские `Talent.dbc`/`TalentTab.dbc` данные уже существуют с `0.7.0.3694`. Между `0.7.0` и `0.8.0` данные физически лежали в клиенте, но фича была выключена/недоступна на практике — это уже вне того, что видно по файлам клиента (вероятно server-side гейтинг или ещё не собранный UI-доступ). **Сознательное решение**: наш экстрактор ориентируется только на факт наличия данных в файлах конкретного билда, не пытается моделировать реальную историческую доступность фичи игрокам — рисуем дерево для Mage начиная с `0.7.0.3694`, даже если оно тогда было недоступно в реальной игре.
  **Два debug-таба существовали только `0.7.0.3694`–`0.8.0.3734`, исчезли к `0.9.0.3807`**: "Test" (classMask `1407` = все классы разом на `0.7.0`, потом `32` на `0.8.0`) и "TomTest" (только на `0.8.0.3734`, icon=0, bg=`Test`) — похоже на личный debug-таб разработчика. После `0.9.0.3807` не встречаются в данных вообще.
  **classMask у Warlock реально переезжал**: на `0.10.0.3892` все 3 warlock-таба (Destruction/Curses/Demonology) уже существуют, но с `classMask=32` (тот же бит, что раньше занимали debug-табы) и без фонового арта (`bg=` пусто). К `0.11.0.3925` classMask меняется на `256` (используется до конца vanilla), появляется арт. **Хардкодить classMask как константу небезопасно для билдов раньше `0.11.0.3925`** — нужно читать из самого DBC, не из справочника.
  **Внутренние имена ассетов не переименовывались вслед за display-именами, и это не только у Warlock** — паттерн повторяется минимум трижды, все три дожили до конца vanilla (проверено на `1.12.1.5875`): Warlock "Curses"→"Affliction" (`BackgroundFile=WarlockCurses`), Warlock "Demonology" (`BackgroundFile=WarlockSummoning`), Paladin **"Retribution"** (`BackgroundFile=PaladinCombat` — таб явно раньше назывался "Combat", потом переименован, а имя ассета нет). Не полагаться на `BackgroundFile`/внутренние имена как на display-имя нигде.
  После исчезновения debug-табов (`0.9.0.3807` и далее) количество табов везде **точно** равно (число классов × 3), без остатка, до самого `1.12.2.6005` — других лишних табов/классов не найдено.
  **TalentTab ID нестабилен и переиспользуется между соседними альфа-билдами — не привязка к классу.** На `0.7.0.3694` в `Talent.dbc` встречаются записи с `TabID=24`, содержащие явно воинские таланты (Axe/Mace/Sword Specialization — подтверждено сверкой по содержимому: в полностью подключённом `1.12.1.5875` эти же спеллы реально лежат в Warrior Arms, `TabID=161`). Но в `TalentTab.dbc` на `0.7.0.3694` существует только 4 таба (ID 1-4, Test+Mage) — `TabID=24` там ни на что не ссылается, это осиротевшая ссылка. Более того, тот же номер `24` на `0.8.0.3734` уже занят СОВСЕМ другим табом ("Test", не Warrior). **Вывод**: класс, которому принадлежит talent-контент на раннем этапе, нужно определять по содержимому спеллов (имя/эффект), а не по числовому `TabID` — на этой стадии альфы ID ещё активно переиспользовались/перенумеровывались.
  **Практическое правило для экстрактора**: `TalentTab.ID` — это ID только внутри ОДНОГО билда, никогда не сопоставлять между билдами (наша схема и так скоупит `talent_tabs`/`talents` по `client_build_id` — это правильно). Но и **внутри одного билда** `Talent.TabID` может не резолвиться ни в одну реальную строку `TalentTab.dbc` (осиротевшая ссылка, пример выше). При записи в MySQL: если `TabID` талант-записи не находится среди реально прочитанных `TalentTab` для этого же билда — **пропускать эту talent-запись с логом**, не писать битой FK-ссылкой.
- **Патч-чейн у vanilla-клиентов — критично, не опционально.** `Talent.dbc` физически лежит в `dbc.MPQ`, но патчится через `patch.MPQ`/`patch-2.MPQ` (если есть — у ранних альфа-клиентов их вообще нет). Открывать нужно `dbc.MPQ` как базовый архив через `SFileOpenArchive`, затем накатывать `patch.MPQ`, потом `patch-2.MPQ` через `SFileOpenPatchArchive` **в этом порядке** — только так `SFileOpenFileEx` отдаёт актуальную версию.
  **Проверено напрямую** (`spike-patch-verify` в `Extractor.Cli`) на `1.12.1.5875`: `dbc.MPQ` сам по себе содержит **устаревший** `Talent.dbc` (36057 байт, sha256 `d78c5a8d…`, версия из 1.12.0), а `patch.MPQ` перекрывает его актуальной версией (36309 байт, sha256 `ebf38e92…`). Без применения патч-чейна экстрактор молча взял бы неправильную (старую) структуру талантов для билда — это не гипотетический риск, а воспроизведённый факт на реальном клиенте.
- **Windows/Linux сборки StormLib должны совпадать по char-width.** Официальный «удобный» бандл `stormlib_dll.zip` — это НЕ то же самое, что промаркированные `RAD`/`RUD`-варианты (проверено по хэшу — не совпадает ни с одним). Взят явно `stormlib_v9.40_amd64_RAD.zip` (Ansi), чтобы совпадать по `TCHAR`-семантике с Linux-сборкой (там `TCHAR=char` всегда) — иначе P/Invoke с `CharSet.Ansi` работал бы только на одной платформе.
- **DllImport на Linux не подхватывает `runtimes/{rid}/native/` из просто скопированных файлов** — это NuGet-конвенция, требующая полноценной deps.json/RID-graph записи (появляется только при реальном упаковывании в NuGet-пакет). Для vendored-бинарников, скопированных вручную через `<None Link=... CopyToOutputDirectory>`, нужно класть файл прямо в корень output-директории (`bin/.../net10.0/libStormLib.so`), тогда стандартный probing по имени библиотеки (`lib<name>.so` / `<name>.dll`) находит его сам.
- **Расширение файла иконки не хардкодить.** `SpellIcon.dbc.TextureFilename` не содержит расширения. Проверено по всему доступному диапазону (`0.5.5.3494`–`1.12.1.5875`, включая самый ранний билд с иконками вообще) — реально везде только `.blp`, ни одного `.tga` не найдено. Тем не менее код (`IconFileResolver`) пробует `.blp`, потом `.tga` через `archive.HasFile(...)`, а не предполагает `.blp` — WoW исторически использовал `.tga` до стандартизации на BLP, и мы не проверяли вообще все существующие клиенты.
- **`SixLabors.ImageSharp` 4.x требует лицензионный ключ при сборке** (новая модель монетизации, build warning). Используем `3.1.12` — последний патч линии 3.x, без этого требования, без известных уязвимостей (в отличие от 3.1.6). Не апгрейдить на 4.x бездумно.
- **`Spell.Description` содержит escape-последовательности (`$s1`, `$d`, `$/1000;S1` и т.д.) — их нужно резолвить В МОМЕНТ ЭКСТРАКЦИИ, не при рендере.** Логика реверс-инжинирена из [sidsukana/QSpellWork](https://github.com/sidsukana/QSpellWork) (`SWObject.cpp::getDescription` + `RegExpX`-семейство), затем сверена буква-за-буквой с тем, что реально встречается в наших 1357 извлечённых vanilla-рангах (`grep` по сырым описаниям) — **не все буквы из QSpellWork вообще нужны**: реально в vanilla talent-текстах используются только `s`/`m` (EffectBasePoints), `d` (SpellDuration), `h` (ProcChance), `o` (периодик: duration/tick × basepoints), `a` (SpellRadius), `u` (стаки), `n` (ProcCharges), `t` (период тика), `b` (комбо-поинты), `l` (грамматика ед./мн. число). Буквы `q`/`v`/`x`/`e`/`z`/`g`/`i`/`m` НЕ встречаются ни разу во всём датасете 1.12.1.5875 (все 432 таланта, 9 классов) — реализованы по минимуму/best-effort, не приоритет.
  Синтаксис: `$[/N; или *N;][spellId]буква[индекс 1-3]` — модификатор делит/умножает, необязательный `spellId` ссылается на ДРУГОЙ спелл (не текущий), индекс — номер эффекта (1-based).
  **Модификаторов сложения/вычитания (`$+N;`/`$-N;`) в grammar нет и не нужно** — проверено CLI-командой `grep-raw-desc <client> <build> <regex>` (грепает СЫРОЙ, ещё не отформатированный `Spell.Description` прямо из DBC, а не то, что уже лежит в БД) по всем 44 извлечённым билдам: ни одного `$` перед `+`/`-`, и шире — ни одного `$` перед любым символом, кроме уже поддержанных `*`, `/`, буквы или цифры. Грамматика `*`/`/` — исчерпывающая для всего диапазона `0.7.0.3694`-`1.12.2.6005`.
  **`$u` (стаки) — в vanilla `Spell.dbc` НЕТ поля `StackAmount`** (в отличие от того, что использует QSpellWork/более поздние версии) — вместо него читаем `CumulativeAura` (единственное похожее по смыслу поле, существующее с `0.7.0.3694`). Подтверждено на реальных данных: "Stacks up to $22959u times" → 5, что совпадает с известным реальным значением Improved Scorch (стакается до 5 раз); аналогично Winter's Chill/Shadow Weaving.
  **`$d` без модификатора добавляет слово "seconds" буквально** (даже для значения 1 — "1 seconds", грамматически странно, но так делает и QSpellWork, и, судя по всему, сам клиент) — только когда НЕТ `/N;`/`*N;` перед ним; с модификатором (например `$/1000;S1 sec`) единица уже прописана вручную в тексте, слово не добавляется.
  **Комбат-рейтинг токены (`$AP`, `$RAP`, `$MWB`, `$MWS` и т.п.)** скейлятся от живых характеристик персонажа — статически посчитать нельзя. QSpellWork просто затирает их пустой строкой; мы вместо этого подставляем читаемый плейсхолдер `<AP>`/`<RAP>`/... (для фронтенда в будущем, если понадобится живая подстановка). **Ни разу не встретились ни в одном из 44 извлечённых билдов** (`0.7.0.3694`-`1.12.2.6005`, все 53857 строк `talent_ranks`, проверено SQL-запросом по всей БД после полной батч-экстракции) — судя по всему, реально не нужны конкретно для дерева талантов (не для `Spell.dbc` в целом, где такие спеллы наверняка есть — оружейные/белый урон и т.п.). Код на них рассчитан на будущее (другие таблицы спеллов вне талантов), но для текущего датасета это мёртвая ветка.
  **Числа форматировать ТОЛЬКО через `CultureInfo.InvariantCulture`.** Без этого `double.ToString()`/`double.Parse()` используют локаль потока — на Windows-машине пользователя с русской локалью числа в `description` записались как "0,1 sec" (запятая) вместо "0.1 sec". Не поймано при тестировании в этом Linux-контейнере, т.к. его дефолтная культура уже даёт точку — поймано только после реального прогона пользователем на его Windows. Текст идёт в БД, а не сразу на экран — не должен зависеть от локали машины, на которой запущен экстрактор.
  Всё реализовано в `Extractor.Dbc.SpellDescriptionFormatter`, вызывается в `BuildExtractor` при формировании `talent_ranks.description` — форматирование делается один раз при экстракции, чтобы не переэкстрачивать билд повторно только ради текста (round-trip на удалённую БД — дорогая операция, см. `BuildExtractor` docblock).
- **`IconPipeline` тоже нужен in-memory кэш поверх `IIconSourceStore`, не только персистентный.** Одна и та же иконка переиспользуется многими рангами/табами В ПРЕДЕЛАХ ОДНОГО прогона (реальные цифры: 273 ranks → только 105 уникальных иконок на первом частичном прогоне) — без in-memory кэша каждое повторное обращение всё равно било round-trip'ом в БД проверить "та же ли иконка", хотя за время одного прогона она гарантированно не меняется.
- **`DATABASE_URL`'s `serverVersion` должен совпадать с реальным сервером, иначе Doctrine видит фантомные diff'ы.** Реальный сервер пользователя — **MariaDB 10.11.6**, а не MySQL (проверять: `SELECT VERSION()`). Указание `serverVersion=8.0.32` (MySQL) вместо `serverVersion=10.11.6-MariaDB` заставляло `doctrine:schema:validate`/`schema:update --dump-sql` находить ложные различия в колонках (Doctrine генерирует DDL под неверный диалект). Формат для MariaDB — `serverVersion=X.Y.Z-MariaDB` (пример уже был закомментирован в дефолтном `.env` из коробки).
- **PHP/Composer не было в этом контейнере — поставлены.** PHP 8.3.33 через Sury-репозиторий (`update-alternatives --set php /usr/bin/php8.3`), Composer 2.10.3 через официальный installer (с проверкой SHA-384 подписи). - **Не поднимать Docker/локальный MySQL.** Сознательное решение: у пользователя уже есть удалённый MySQL-сервер, а разработка соло внутри уже контейнеризированного Debian-окружения поверх WSL2 — вложенный Docker добавляет риск (доступ к docker-сокету, nested-виртуализация) без реальной выгоды на этом этапе.
- **WoWDBDefs (`.dbd`) сравнивает билды по кортежу `(major, minor, patch, build)`, а не по сырому номеру билда — из-за этого в самом upstream-репозитории бывают реальные "дыры" между соседними диапазонами.** Реально пойманы на батч-прогоне всех билдов: `extract-build` падал с `System.IO.FileNotFoundException: No definition found for this file` на `1.0.1.3989` и `1.1.0.4044` — ни `ChrClasses.dbd`, ни (для первого билда) `Spell.dbd` не покрывали их диапазонами (`BUILD 1.0.0.3980` соседствует с `BUILD 0.5.5.3494-0.12.0.3988`, а `1.0.1.3989` попадает МЕЖДУ ними по кортежному сравнению, хотя по номеру билда 3989 спокойно лежит внутри диапазона 3494-3988). Не гипотеза — подтверждено новым CLI-спайком `raw-dbc-header <client> <TableName>` (печатает сырой WDBC-заголовок: recordCount/fieldCount/recordSize без всякой DBCD-схемы): `1.0.1.3989`'s `ChrClasses.dbc`/`Spell.dbc` побайтово (recordSize/fieldCount) совпадают с `1.0.0.3980`, а `1.1.0.4044`'s `ChrClasses.dbc` совпадает с `1.1.1.4062`. Остальные 4 вендоренные таблицы (`Talent`/`TalentTab`/`SpellIcon`/`SpellDuration`/`SpellRadius`) используют один сплошной диапазон на весь vanilla-релиз (`1.0.0.3980-1.12.3.6141`) и такой дыры не имеют.

- **`php -S` для локальной разработки Symfony требует router.php, и этот router.php ОБЯЗАН делать `return require`, а не просто `require`.** Без router-скрипта встроенный сервер PHP не проксирует произвольные пути во `index.php` — реально проксируется только `/` (для остальных путей — голый 404 от самого сервера, минуя Symfony целиком). Обычный fix — router-скрипт, который отдаёт реальные файлы (`storage/icons/*.png`, ассеты) напрямую и всё остальное шлёт в `index.php`. **Но** `symfony/runtime`'s `vendor/autoload_runtime.php` внутри себя делает `require $_SERVER['SCRIPT_FILENAME']`, ожидая получить замыкание, создающее Kernel — а под `php -S` с указанным router-скриптом `SCRIPT_FILENAME` для ЛЮБОГО пути равен router-скрипту, а не `index.php`. Т.е. этот `require` рекурсивно требует САМ router.php ещё раз. Если router.php вызывает `require __DIR__.'/index.php';` БЕЗ `return`, то возвращаемое index.php замыкание никуда не попадает — снаружи `require` router.php возвращает дефолтный `1` (int), и Symfony падает с `TypeError: Invalid return value: callable object expected, "int" returned`. Воспроизведено буквально — сначала на статике (`/icons/*.png`, когда router.php ещё не проверял файл на диске и просто требовал index.php без return), затем на любом Twig-роуте после добавления той самой проверки на файл. Фикс — `return require __DIR__.'/index.php';` в router.php.
- **`PHP_CLI_SERVER_WORKERS>1` держит скомпилированные классы в памяти между запросами.** Без этой переменной `php -S` однопоточный — панель браузера шлёт HEAD-запросы на `/` каждые ~4 секунды (похоже на heartbeat/speculative-preconnect) и полностью забивает очередь одного воркера, любой другой запрос (включая curl) виснет на десятки секунд/таймаутится. Поставили `PHP_CLI_SERVER_WORKERS=4` (через `env PHP_CLI_SERVER_WORKERS=4 php -S ...` в `.claude/launch.json`, раз сам конфиг лаунчера не поддерживает произвольные env-переменные) — но после этого КАЖДОЕ изменение PHP-кода в `web/src/` требует перезапуска сервера (воркеры — долгоживущие процессы, не перечитывают файлы между запросами, в отличие от классического `php-fpm`/`opcache.validate_timestamps=1` с коротким TTL).
- **`.ps1`-скрипты с не-ASCII символами (даже просто `—` вместо `-`) ломают Windows PowerShell "missing terminator".** Воспроизведено на реальном запуске `Extract-AllBuilds.ps1`: файл был сохранён как UTF-8 без BOM; `powershell.exe` (Windows PowerShell 5.1, не `pwsh`/PowerShell 7) без BOM читает `.ps1` в системной ANSI-кодировке, а не UTF-8. Байты UTF-8 символа `—` (em dash, `E2 80 94`) при таком неверном чтении превращаются в другие символы внутри уже открытой строки — парсер теряет закрывающую кавычку и падает с `TerminatorExpectedAtEndOfString`/`Missing closing '}'`, причём сама ошибка указывает на строку/фигурную скобку значительно ПОСЛЕ настоящей причины. Фикс — держать все `.ps1`-файлы чистым ASCII (см. `conventions.md`); альтернатива (не выбрана) — сохранять с UTF-8 BOM.
